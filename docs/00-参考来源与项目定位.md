## 一、项目是什么

从零做一个 **DeepSeek Harness（dsh）的生图工作台插件**。

装上后 dsh 侧边栏多一个「生图」入口，点进去是完整的独立页面——顶部标签页切换普通生图 / 画廊 / 无限画布 / 电商模式，不是只能在对话里打字调工具。

自己本地跑，自己用。

**是重做，不是 fork、不是二次开发。** 下面列的项目都是参考：看它们的功能设计、交互形态、协议适配思路，然后自己实现。

## 二、主程序（宿主环境）

### DeepSeek Harness

- **仓库**：https://github.com/deepseek-ai/DeepSeek-Harness
- **是什么**：DeepSeek 官方的 agent 运行环境。本项目是它的一个插件
- **插件机制**：基于 Cordis（服务容器 + 插件系统）
- **状态**：开发者预览期，接口会有破坏性变更 → 锁定一个版本并在项目里记录下来

### 插件怎么写

- **教程仓库**：https://github.com/DumplingHuman/dsh-plugin-tutorial

已读过，要点摘录（**实现前仍要完整读一遍原文**，本项目文档不重复它的内容）：

- 插件 = 导出 `apply(ctx, config)` 的模块，用 `inject` 声明依赖哪些服务
- `ctx` 是服务容器，能力挂在 `ctx.xxx` 上
- 注册即副作用，插件卸载时自动清理，不用手动善后
- 事件有多种分发模式：广播、并行、串行、拦截式中间件
- 配置用同名 `Config` 接口 + schema 声明，默认值写在 schema 里
- 凡不同部署可能取不同值的参数，一律做成配置项，不硬编码

## 三、参考谁的代码

### Nova Image Studio —— 功能范围参考

- **仓库**：https://github.com/tianjiangqiji/nova-image-studio
- **形态**：独立 Web 应用（Next.js），不是 dsh 插件

**Nova 的七种工作模式**（本项目全部覆盖）：

| Nova 模式 | 说明 |
|---|---|
| 文生图 | 文字出图，可并行多张 |
| 图生图 | 上传参考图编辑 / 转换 / 改风格 |
| Agent 模式 | 对话式生成，带视觉描述、联网搜索、推理 |
| UI 设计模式 | 设计稿切图 → 复刻网页（仅宽屏） |
| 反推提示词 | 上传图片流式反推提示词 |
| GIF 生成 | 多帧生成 + 网格拼装 + 浏览器内编码 |
| 视频工作台 | Nova 用插件包实现；**本项目改为内置** |

**其他可参考的点：**

- 多模型配置：每个模型独立的协议、显示名、模型 ID、密钥、地址、最大参考图数、最大分辨率
- 可为每种用途分别设默认模型（文生图 / 图生图 / 反推 / Agent / 切图 / 网页复刻 / 切片编辑）
- 任务队列：服务端并发处理，WebSocket 推进度，失败降级为 HTTP 轮询
- 重启后把残留的"处理中"任务标记为失败，不留幽灵任务
- 提示词广场
- 备份 / 还原
- 历史图片懒加载

**和本项目的差异：**

- Nova 是独立 Web 应用（Next.js + 自建 server.js + SQLite + WebSocket）。本项目是 dsh 插件，任务、存储、会话用 dsh 宿主能力，**别把它那套后端搬过来**
- Nova 的视频靠插件包（三个 JSON 文件）扩展。**本项目视频协议内置**——本身已经是插件了，不再套一层

### dsh-imagegen（界面名 VisioWork）—— 形态参考

- **仓库**：https://github.com/dickpy/dsh-imagegen
- **npm**：`@dickpy/dsh-imagegen`（参考版本 1.5.12）
- **形态**：已经在 dsh 上跑起来的生图工作台插件，就是本项目想要的样子

**这是最直接的形态参照。它的 README 写得很细，把每个页面的交互都讲清楚了，值得完整读一遍。**

参考这些：

- 侧边栏「新会话 / 生图」双 Tab 的入口方式
- 顶部标签页：普通生图 / 素材库 / 无限画布 / 电商模式
- 三栏布局：历史记录 | 生图区 | AI 对话（对话默认收起，宽度可拖并记忆）
- 参数档位：9 档比例、4 档清晰度、1–4 张
- 无限画布的节点 + 连线交互
- 电商套图「先出计划预览，确认后再批量生成」的流程
- 画廊的筛选、瀑布流、标签、按内容去重
- 多渠道配置 +「检测可用模型」

**协议适配范围**（它已经踩过的坑，本项目要覆盖同样的范围）：

- 标准 OpenAI `/images/generations`、`/images/edits`
- 异步两步式接口：提交返回 `task_id`，需轮询到完成
- Grok Imagine、Nano Banana / Gemini 图像系列、Seedream（豆包）、Qwen-Image（通义，走 DashScope 原生接口而非 OpenAI 兼容）、智谱 GLM-Image、MiniMax image-01

## 五、技术栈

| 项 | 选择 |
|---|---|
| 宿主 | DeepSeek Harness |
| 插件框架 | Cordis（dsh 自带） |
| 运行环境 | Node.js 20+ |
| 模块格式 | ESM |
| 包管理 | pnpm |
| 前端 | 【自定】需要支持节点画布 |
| 数据存放 | 本地用户目录，默认 `~/.dsh/<插件名>/` |

前端框架没有硬性规定，选一个能做出节点画布的即可。**这是技术选型里唯一需要认真权衡的点**——无限画布是最复杂的页面。

## 六、一条实现原则

**不要加任何限制生成的功能。** 不做内容审查、不做敏感词过滤、不做"这个我不能生成"、不做评分不够就禁止出图、不做强制二次确认。

工作台的职责是把图稳定地生出来，不是判断用户该不该生成。

这条最容易在 skill 部分被违反：那几个 skill 里写了打分表和"低于 82 分重做"。**那是作者写给自己的创作自律，不是给工具的拦截规则。** 实现时把分数显示出来就行，出图按钮永远可点。
